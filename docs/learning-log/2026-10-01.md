## 学んだ概念

### データ基盤の基本

- **OLTP と OLAP**: 運用DBは「今の状態」を1件ずつ読み書きする。分析基盤は、履歴を持ち、複数のソースを統合し、大量の行を集計する。分析基盤を別に建てる本当の理由は、履歴と統合
- **データレイクと DWH**: レイクは生データを置き、読むときに解釈する（schema-on-read）。DWH は書くときに型を決める（schema-on-write）。S3 と Athena の組み合わせは、両方を兼ねる「レイクハウス」
- **Athena の課金**: 実行時間ではなく、読んだデータ量で課金される（1TB あたり約 $5、1クエリの最低は 10MB）
- **パーティション**: `snapshot_date=2026-10-01/` のような Hive 形式のプレフィックスにすると、Athena がその部分を列として扱い、絞り込んだ日だけを読む（パーティションプルーニング）。日付をファイル名に入れるだけでは絞り込めない
- **Parquet**: 列ごとにまとめて保存するので、必要な列だけを読める。型を持ち、圧縮が効く。CSV は、値の中の改行やカンマで行がずれ、型も失われる
- **スタースキーマ**: 数値（ファクト）と、切り分ける軸（ディメンション）に分ける。ファクトの**粒度**（1行が何を表すか）を最初に決める
- **3つがつながる**: 読んだ量で課金される → パーティションで読むファイルを減らし、Parquet で読む列を減らす

### データの扱い

- **全量スナップショット**: 毎回 DB 全体を取る。単純で壊れにくいが、データが大きいと重い。対になるのは増分取り込みと CDC。clips.db は約 740KB なので全量で十分
- **更新されるデータの扱い**: 過去のスナップショットは書き換えず、翌日の分を新しいパーティションとして足す。日ごとの差分から、いつ変わったかがわかる。1日のうちに2回変わった場合の途中の状態は残らない
- **SCD Type 2**: 「この値は何日から何日まで有効だった」という形で履歴を持つ方法。dbt snapshot で作る
- **冪等性**: 同じ処理を2回実行しても結果が変わらないこと。同じ日のパーティションを上書きする設計が、その最初の例
- **raw と curated の層**: raw は取ってきたまま書き換えない。curated は raw から何度でも作り直せる

### Terraform

- **IaC**: インフラのあるべき姿をコードで宣言する。Vue.js がテンプレートと仮想DOMの差分で画面を更新するのと同じ考え方で、`plan` で差分を予告し、`apply` で反映する
- **コードと state は別物**: コード（`.tf`）はあるべき姿で、Git で管理する。state は実際に作ったものの記録で、機密を含むので Git に入れない。PC が壊れて失われるのは state
- **リモートバックエンド**: state を S3 に置くと、PC の故障、CI からの参照、同時実行の衝突を解決できる。ロックは S3 のネイティブロック（Terraform 1.10 以上）で行える
- **鶏と卵の問題**: state 用バケットを Terraform で作るには、その state の置き場所が要る。bootstrap 用の小さな Terraform をローカルの state で作り、できたバケットに state を移して解決する

### 権限

- **最小権限の原則**: 必要な操作だけを許可する。誤操作と、認証情報が漏れたときの被害を小さくする
- **何を許可しないかにも理由がある**: 同名で上書きすれば削除権限は要らない。`aws s3 cp` なら一覧の権限は要らない。使うコマンドが必要な権限を決める
- **長期間有効な鍵を持たない**: IAM ユーザーのアクセスキーより、Identity Center の一時的な認証情報を使う
- **バケットポリシーの Deny はロールの Allow より優先される**: ReadOnlyAccess で全バケットが読める状態でも、tfstate バケット側で拒否できる
- **IAM が主、settings.json は補助**: settings.json の deny はローカルのコマンドやファイルの文字列で判定されるので、S3 上の state の読み取りは止められない

### Athena と Glue

- **Glue Data Catalog**: Athena にデータの場所・列・型・形式を教える定義。Athena 自体はデータを持たない
- **パーティション射影**: 日付の規則をテーブル定義に書き、Athena がクエリのたびにプレフィックスを計算する。登録作業も追加の権限も要らない

### 分析の設計

- **データプロファイリングを先に**: ゴールを決める前に、データの件数や実態を確かめる。スキーマだけを見て「スコアで再生数を予測する」をゴールにしたが、件数を数えると投稿済みのショートは10件しかなかった
- **サンプルの独立性**: 長尺の候補は113件あるが、再生数は動画単位なので、そのまま比べると実質13件。動画内の位置ごとに取れる維持率を使えば、候補ごとの成果になる
- **動画内比較（固定効果の考え方）**: 同じ動画の候補どうしを比べれば、動画ごとの人気の差を打ち消せる
- **公平な比較と選択バイアス**: 累計の再生数は投稿日によって変わる。成果があるのは投稿されたものだけ
