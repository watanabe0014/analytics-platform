# ADR-0005: Athena のテーブル定義は Terraform で書き、パーティションは射影で扱う

- 日付: 2026-10-01
- 状態: 承認

## 背景

- Athena はデータを持たず、クエリのたびに S3 を読む。どこにどんな列のデータがあるかは、Glue Data Catalog のテーブル定義で教える
- `curated/` の Parquet は、テーブルごと・日付（`snapshot_date=YYYY-MM-DD/`）ごとに毎日1つずつ増える（ADR-0003）
- Athena は、新しくできたパーティションを自動では認識しない
- アップロードの権限は、data バケットへの書き込みだけに絞っている（ADR-0004）
- Parquet の型は、変換スクリプトで明示する（ADR-0002）

## 決定

### テーブル定義は Terraform で書く

- `aws_glue_catalog_database` と `aws_glue_catalog_table` で、列・型・形式（Parquet）・場所を定義する
- 列と型の定義はスキーマ設計にあたるため、ユーザーが書き、Claude がレビューする

| 方法 | 採否 | 理由 |
|---|---|---|
| Terraform | **採用** | コードで管理でき、型を明示できる。費用がかからない |
| Athena の DDL（`CREATE EXTERNAL TABLE`） | 不採用 | 手で実行した SQL は記録に残らず、IaC の方針に反する |
| Glue クローラー | 不採用 | 型が推測になる（例: `score` が整数だけの日に `bigint` と推測されうる）。毎日実行すると月 $2 前後かかる |

### パーティションは射影で扱う

- テーブルのプロパティで、パーティション射影（partition projection）を有効にする
  - `snapshot_date` を `date` 型の射影として、形式を `yyyy-MM-dd`、範囲を `<最初のスナップショットの日>,NOW` とする
- Athena は、クエリのたびに規則からプレフィックスを計算する。パーティションを登録する作業は要らない

| 方法 | 採否 | 理由 |
|---|---|---|
| `ALTER TABLE ... ADD PARTITION` | 不採用 | 毎日の登録作業が要る。アップロードの権限に、Athena の実行・Glue への書き込み・athena-results への書き込みを足す必要がある |
| `MSCK REPAIR TABLE` | 不採用 | 上に加えて、S3 の一覧を見る権限も要る。パーティションが増えるほど遅くなる |
| パーティション射影 | **採用** | 登録の作業も、追加の権限も要らない。日付が1日1つ決まった形で増えるこのデータに合う |

## 結果

- アップロードの権限を、ADR-0004 の最小のまま保てる
- スナップショットを置いた直後から、Athena でクエリできる
- 型の定義が、変換スクリプト（Parquet の型）と Terraform（テーブルの型）の2か所に分かれる。両者がずれると Athena がエラーになるため、型の対応表を1か所で決め、両方をそれに従わせる
- 射影を有効にしたテーブルでは、Glue に登録したパーティションは無視される
- 範囲内でデータがない日を指定しても、エラーにはならず0件が返る
- `snapshot_date` で絞らずにクエリすると、範囲内のすべての日のプレフィックスを見に行く。日付で絞るのを習慣にする

## 残る課題

- 型の対応表をどこに置くか（ドキュメントにするか、変換スクリプトと Terraform の両方が読む設定ファイルにするか）
- dbt（フェーズ2）では、このテーブルを source として参照する。dbt が作るテーブル（staging、marts）の定義は dbt 側で管理する
