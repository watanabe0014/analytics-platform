# ADR-0002: clips.db のスナップショットは、元の .db とテーブルごとの Parquet の両方を S3 に置く

- 日付: 2026-10-01
- 状態: 承認

## 背景

フェーズ1の完了条件は「clips.db のスナップショットを S3 に置き、Athena で SQL が打てる」こと。

- Athena は SQLite のファイル形式を読めない。読めるのは CSV、JSON、Parquet、ORC など
- clips.db は稼働中のアプリが書き込んでいる。書き込み中に `cp` でコピーすると、壊れたコピーができることがある
- clips.db には、CSV にすると壊れやすい列がある
  - 改行やカンマを含む文章（`description_final`、`title_final`）
  - JSON の列（`score_breakdown`、`cast_speaker_ids`、`style_snapshot`）
- clips.db の大きさは約 740KB（2026-10-01 時点）

## 検討した選択肢

| 案 | 内容 | 採否 |
|---|---|---|
| テーブルごとの CSV | 実装が最も簡単 | 不採用。値の中の改行・カンマで行がずれる。型が失われ、NULL と空文字を区別できない |
| テーブルごとの Parquet | 列ごとに型を持ち、列指向で Athena のスキャン量が少ない | **採用** |
| 元の .db ファイル | そのままでは Athena で読めない | **Parquet と併せて保存する** |

## 決定

- スナップショットは、SQLite のバックアップ機能（`sqlite3` の `.backup`、または Python の `sqlite3.Connection.backup()`）で取る。`cp` は使わない
- S3 には次の2つを置く
  1. **元の .db ファイル**: 生データとして残す。変換の方法を変えたときに、ここから作り直せるようにする
  2. **テーブルごとの Parquet**: Athena でクエリする対象
- 変換は Python で書く
- Parquet に変換するときは、列の型を明示する（SQLite の型の宣言は実際の値を保証しないため）
  - `DATETIME` の列は、文字列からタイムスタンプに変換する
  - `BOOLEAN` の列（実際には 0 と 1）は、真偽値に変換する
  - JSON の列は文字列のまま入れ、Athena の `json_extract` などで読む

## 結果

- Athena でクエリでき、スキャン量も抑えられる
- 変換を誤っても、元の .db から作り直せる
- 型の対応表（SQLite の列 → Parquet の型）を、自分で設計して管理する必要がある
- 保存量は、毎日置いても年に数百 MB で、月額は $0.01 未満

## 残る課題

- 変換に使うライブラリ（DuckDB、または pandas と pyarrow）は実装時に比べて決める
- S3 の中の置き方（日付ごとに残すか、パーティションをどう切るか）は論点3で決める
