# ADR-0006: YouTube API の認証には、test-app と別の Google Cloud プロジェクトを使い、同意画面を本番にする

- 日付: 2026-10-01
- 状態: 承認

## 背景

- YouTube Analytics API と YouTube Reporting API は、API キーでは使えず、チャンネル所有者の OAuth 認証が要る
- test-app は、動画の投稿のために、すでに Google Cloud プロジェクトと OAuth クライアントを持っている
- 同意画面（OAuth consent screen）が「テスト」のままだと、リフレッシュトークンは7日で失効する。フェーズ3の定期実行が成り立たない
- 同意画面の設定（公開状態、スコープ）と API のクォータは、**プロジェクト単位**で効く。クライアント単位ではない
- 同意画面と、外部ユーザー向けの OAuth クライアントは、Terraform の google provider で管理できない
- Reporting API のジョブには管理画面がなく、API（`jobs.create`）を呼んで作る

## 決定

### 1. 分析用に Google Cloud プロジェクトを新しく作る

test-app のプロジェクトと OAuth クライアントは使わない。

| 観点 | 共用した場合に起きること |
|---|---|
| API のクォータ | YouTube Data API のクォータ（1日 10,000 ユニット）はプロジェクト単位。動画のアップロードは1回 1,600 ユニット前後を使う。分析側の呼び出しが増えると、test-app の投稿が止まりうる |
| 影響範囲 | シークレットが漏れてクライアントを作り直すと、両方のシステムが同時に止まる |
| 設定変更の巻き込み | 同意画面のスコープや公開状態の変更が、もう一方にも効く |
| 最小権限 | 分析用のプロジェクトには、読み取り専用のスコープと必要な API だけを登録すればよい |

### 2. 同意画面は「本番」にし、審査は受けない

- 利用者は自分だけなので、「未確認のアプリ」の警告は自分で進める
- 本番に切り替えてから認可する。テスト中に発行したトークンは使わない
- 登録するスコープは読み取り専用に限る
  - `https://www.googleapis.com/auth/yt-analytics.readonly`（Analytics API、Reporting API）
  - `https://www.googleapis.com/auth/youtube.readonly`（Data API で動画の一覧やメタデータを取る場合）
  - 収益のスコープ（`yt-analytics-monetary.readonly`）は登録しない。分析のゴールに不要で、収益額はこのリポジトリに入れない

### 3. Google Cloud の作業は、作業の性質で扱いを分ける

| 作業 | 扱い |
|---|---|
| プロジェクトの作成、API の有効化、同意画面、OAuth クライアント | `docs/setup/google-cloud-setup.md` に手順を書き、手で行う。CLAUDE.md の「手動操作の例外」に加える |
| Reporting ジョブの作成、レポートの取得 | API の呼び出しなので、リポジトリにスクリプトとして置く |

プロジェクトの作成と API の有効化は google provider で管理できるが、Terraform にしない。gcloud の認証、2つ目の provider、その state を増やすほどの価値がない。どれも一度作れば変えないリソースである。手順書とスクリプトがあれば、IaC の目的である「再現できること」と「レビューできること」は満たせる。

## 検討した選択肢

| 案 | 採否 |
|---|---|
| test-app のプロジェクトとクライアントを共用する | 不採用。上の表の理由による。手間が省けるのは利点だが、分ける作業は15分ほどで済む |
| test-app のプロジェクトに、分析用のクライアントだけを追加する | 不採用。クォータと同意画面はプロジェクト単位なので、問題の大半が残る |
| 同意画面を「テスト」のまま、7日ごとに手で認可し直す | 不採用。定期実行が成り立たない |
| 審査を受けて「確認済み」にする | 不採用。利用者は自分だけで、審査の手間に見合わない |
| プロジェクトと API の有効化を Terraform で管理する | 不採用。上の理由による。リソースが増えたら見直す |

## 結果

- 分析側の失敗や事故が、test-app の投稿に波及しない
- 7日での失効がなくなる。ただし、次の場合はトークンが失効するので、フェーズ3で検知の仕組みを作る
  - 6か月使わなかったとき
  - ユーザーがアクセスを取り消したとき
  - 同じクライアントとアカウントの組み合わせで、リフレッシュトークンの発行数が上限（100本）を超えたとき（古いものから無効になる）
- 認可のたびに「未確認のアプリ」の警告画面を通る
- OAuth のクライアントシークレットとトークンは、ローカルの `.gitignore` 済みのファイルに置く。フェーズ3で Lambda に移すときに、保管場所（Secrets Manager など）を決める

## 残る課題

- test-app の同意画面が「テスト」のままなら、test-app のトークンも7日で失効している可能性がある。clips.db の更新が 2026-09-20 で止まった理由の候補。test-app 側で確かめる（このリポジトリの範囲外）
