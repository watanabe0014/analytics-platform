# アーキテクチャとロードマップ

最終更新: 2026-10-01
状態: 合意済み

切り抜き動画の自動作成システム（以下、test-app）の運用データと、YouTube の成果データを集めて分析する基盤を、AWS 上に段階的に作る。個々の設計判断の理由は `docs/adr/` にある。

---

## ゴール

### 主目的①: 長尺動画の候補スコアは、その区間の視聴者維持率を予測できているか

- test-app は長尺動画を作るとき、元の配信から区間の候補を切り出し、スコア（`longform_candidates.score`、内訳は `score_breakdown`）を付けて選ぶ
- 投稿した長尺動画の視聴者維持率（YouTube Analytics API の `audienceWatchRatio` など）を、各候補が動画のどの位置にあたるかに重ねて、候補ごとの成果を求める
- 結果を、スコアの重みの調整に戻す（フィードバックループ）。逆方向の問い（視聴者を引き留めた区間はスコアも高かったか）も確かめる

**この形にした理由:** 当初は「切り抜きショートのスコアで再生数を予測できるか」を考えていたが、データを確かめると投稿済みのショートは10件しかなく、統計的に意味のある比較ができなかった。長尺動画の候補は、投稿済み13本の中に113件ある。再生数は動画単位でしか取れないため、そのまま比べると実質13件になる。そこで、動画内の位置ごとに取れる維持率を成果として使う。

### 副次目的②: いつ出すと伸びるか

- 投稿の曜日・時刻、元配信の公開から投稿までの時間（鮮度）と、成果の関係を見る

## 前提（2026-10-01 時点）

### データソース

| ソース | 内容 | 取り方 |
|---|---|---|
| clips.db（SQLite、約 740KB） | test-app の運用DB。稼働中のアプリが書き込む | 直接読まず、SQLite のバックアップ機能でスナップショットを取る |
| YouTube Analytics API | 動画 × 日の再生数・高評価・視聴時間、動画内の位置ごとの視聴者維持率 | 過去の期間も後から問い合わせられる |
| YouTube Reporting API | サムネイルのインプレッション数とクリック率（レポート `channel_reach_basic_a1`） | Analytics API にない指標。ジョブを作った日の30日前より古い分は取れない。レポートは生成から60日（さかのぼって作られた分は30日）で消える |

どちらの YouTube API も、APIキーでは使えず、チャンネル所有者の OAuth 認証が要る。

### 分析に使えるサンプル数

| 投稿物 | テーブル | 投稿済み | スコアの持ち方 |
|---|---|---|---|
| 切り抜きショート | `clips` | 10件（全335件。EXPIRED 258、REJECTED 63、FAILED 4） | `clips.score` |
| 長尺 | `longform_projects` | 13件（採用された候補は113件） | 候補ごと（`longform_candidates`） |
| 長尺から作ったショート | `longform_shorts` | 6件 | 元の候補（`candidate_id`） |
| まとめ動画 | `compilations` | 0件 | — |

- 4種類とも `youtube_video_id` を持ち、成果データとつなげられる
- `metrics`（clip × 日）と `vod_chat_stats` は0件

## 技術選定

| 領域 | 選定 | 理由 |
|---|---|---|
| IaC | Terraform | AWS 以外も同じ書き方で扱える。state は S3 に置く（ADR-0001） |
| 保存 | S3（Parquet） | 列指向で、Athena のスキャン量と費用を抑えられる（ADR-0002） |
| クエリ | Athena ＋ Glue Data Catalog | サーバーレスで、使った分だけ課金される。常時起動のリソースが要らない |
| 変換 | dbt Core（dbt-athena） | SQL でテスト付きのモデルを作れる。無料でローカル実行できる |
| 取り込みの処理 | Python（スクリプト、のちに Lambda） | dbt、Google の API ライブラリと言語をそろえられる |
| 定期実行 | EventBridge Scheduler | 無料枠が大きく、常時起動のリソースが要らない |
| 可視化 | ローカルの Notebook、または Evidence.dev など | QuickSight は1人あたり月 $20 前後かかるため避ける |

## ロードマップ

| フェーズ | 作るもの | 学べる概念 | 想定月額 | 転職でアピールできる点 |
|---|---|---|---|---|
| **1. 最小のレイク** | state 用バケット（bootstrap）、data と athena-results のバケット、`yt-uploader` の権限セット、Glue のテーブル定義（パーティション射影）、Athena のワークグループ、スナップショットと Parquet 変換のスクリプト（手動実行） | Terraform（state、plan、apply、bootstrap）、S3 の設計、Hive 形式のパーティション、最小権限、schema-on-read、Athena の課金モデル | $0〜0.5 | IaC でゼロから、コストと権限を意識して分析環境を建てた |
| **2. 変換とモデリング** | dbt-athena による staging → marts の層、スタースキーマ、dbt test、dbt snapshot（状態の履歴） | スタースキーマ、粒度の設計、SCD Type 2、データ品質テスト、レイヤー設計 | $0〜1 | dbt でテスト付きのデータモデルを設計した |
| **3. 取り込みの自動化** | Python の Lambda（EventBridge Scheduler で日次実行）による3つの取り込み: Analytics API（日次の指標、維持率）、Reporting API（インプレッション、CTR）、スナップショットの定期アップロード。OAuth トークンの安全な保管 | 増分取り込み、冪等性、秘密情報の管理、OAuth の失効対策、Lambda の実行ロール、依存ライブラリの同梱 | $0〜1 | 性質の違う外部 API の取り込みを、再実行しても安全に作った |
| **4. 分析と還元** | ①候補スコアと維持率の関係の分析、②投稿タイミングの分析、重み調整案の test-app への反映 | 分析設計（公平な比較、選択バイアス、動画内比較）、可視化、指標の定義 | $0〜1 | 分析でプロダクトの改善を回した |
| **5. 運用品質** | 取り込みの失敗・データ欠損の通知（SNS）、GitHub Actions による CI（terraform plan、dbt build、OIDC）、コスト監視 | オブザーバビリティ、CI/CD、OIDC によるキーレス認証、データの鮮度監視 | $0〜1 | 運用まで設計した |

**全体の月額の見込み:** $1〜3 程度。データは MB 単位で、常時起動のリソースを使わない。

**順序の理由:** データ寄りの学習（SQL、スキーマ設計）をじっくり行うため、モデリング（フェーズ2）を自動化（フェーズ3）より先にする。Analytics API の指標は過去の分を後から取れるので、取り込みを遅らせても失われない。

### フェーズ1と並行して前に出す作業

自動化を後回しにする代わりに、取り返しのつかないものだけを先に行う。

| 作業 | 理由 |
|---|---|
| Reporting API のジョブを作る | 作るのが1日遅れるごとに、取れないインプレッションのデータが1日分増える |
| Reporting のレポートを手動で取得する（自動化まで、30日以内の間隔で） | 自動化するまでの間に、レポートが消えるのを防ぐ |
| 長尺1〜2本の維持率を、1回だけ手で取る | 維持率が取れるかはゴール①の前提。レスポンスの形をモデリングの設計に使う |

## フェーズ1の構成

```
test-app/data/clips.db
   │ SQLite のバックアップ機能で複製（ローカル）
   ▼
スナップショットの .db ──(Python で Parquet に変換、型を明示)──┐
   │                                                      │
   │ yt-uploader で書き込み                                │
   ▼                                                      ▼
s3://<data>/raw/clips_db/snapshot_date=YYYY-MM-DD/clips.db
s3://<data>/curated/clips_db/<テーブル>/snapshot_date=YYYY-MM-DD/part-0.parquet
                                                          │
                     Glue Data Catalog（Terraform で定義、パーティション射影）
                                                          │
                                                          ▼
                                   Athena（結果は s3://<athena-results>/、7日で削除）
```

| 決めたこと | ADR |
|---|---|
| state は S3 に置き、state 用バケットは bootstrap 用の Terraform で作る | [ADR-0001](adr/0001-terraform-state-backend.md) |
| スナップショットは、元の .db とテーブルごとの Parquet の両方を置く | [ADR-0002](adr/0002-snapshot-format.md) |
| バケットは用途ごとに3つ。スナップショットは全量を日付のパーティションで残す | [ADR-0003](adr/0003-s3-layout.md) |
| アップロードは、data バケットに書くだけの権限セット `yt-uploader` で行う | [ADR-0004](adr/0004-upload-permissions.md) |
| テーブル定義は Terraform で書き、パーティションは射影で扱う | [ADR-0005](adr/0005-athena-table-definitions.md) |

**完了条件:** clips.db のスナップショットを S3 に置き、Athena で SQL が打てる。

## 分析の注意点（フェーズ4で扱う）

1. **公平な比較:** 再生数は、投稿してからの日数とともに増える。投稿日の違う動画の累計値を、そのまま比べない
2. **選択バイアス:** 成果があるのは投稿されたものだけ。採用されなかった候補の成果は測れない
3. **候補どうしは独立していない:** 同じ動画の候補は、動画自体の人気の影響を一緒に受ける。動画をまたいで比べず、同じ動画の中で「スコアの高い候補ほど維持率が高いか」を見る
4. **位置の対応づけは近似:** 候補の尺を `order_no` 順に足して動画内の位置を求めるが、無音のカットなどで実際の位置とずれうる
5. **維持率が取れないことがある:** 再生数の少ない動画では、YouTube が維持率を返さないことがある
